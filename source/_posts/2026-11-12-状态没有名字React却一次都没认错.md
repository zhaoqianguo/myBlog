天天写 `useState`，要我讲清楚它怎么把上次的值找回来，我讲不出来。

规则倒是背得很熟：只在顶层调用，只在 React 函数组件或自定义 Hook 里调用。`eslint-plugin-react-hooks` 的 `react-hooks/rules-of-hooks` 会在代码跑起来之前先把违规标红。可要问为什么，答案多半是「React 需要 hooks 保持同样的顺序」，等于把问题原样复述一遍。今天翻到 Adil Sadqi 那篇《Every React Developer Uses Hooks. Almost None Can Explain How They Work.》，他把这句循环答案直接戳破了，还引了 State of React 2025 的两组数：`useEffect` 有 98% 的人在用，也是抱怨最多的 hook，37% 的人报告过问题，依赖数组排第一。原报告我没去核对，先把出处记下。他那篇的做法很对我的路子：从零把 hooks 系统搭一遍，规则就不再是规矩，而是这套数据结构能活下来的唯一条件。我照这个骨架走了一遍，中间那几段代码都在 Node v22.22.2 上自己跑过。

## 两条规则，和一个循环答案

React 明面上就两条：别在循环、条件、嵌套函数里调 Hook；别在普通 JS 函数里调 Hook。工具链替它守着，`react.dev/reference/rules/rules-of-hooks` 还补了不能进 `try`/`catch`/`finally`、不能放在条件 `return` 之后。

浅一层的解释是「因为 React 靠调用顺序认状态」。这话不算错，可它没说顺序是被什么逼出来的。真要回答，得同时说清两件事：多个 Hook 各自的值放在哪，以及 React 怎么知道这次调用该写进哪个组件的存储。母文里那句 `The rules exist because of a specific data structure. Build the data structure, and the rules stop being rules. They become physics.` 说的就是这个意思。我把它抄在本子第一页。

## 一个全局变量，两个 hook 就撞了

最简的 `useState` 只要做三件事：存一个值、把它返回、给个改值的入口。

```js
let state;

function useState(initialValue) {
  state = state ?? initialValue;
  function setState(newValue) {
    state = newValue;
    rerender();
  }
  return [state, setState];
}

function Counter() {
  const [count, setCount] = useState(0);
  return `Count: ${count}`;
}
function rerender() { console.log(Counter()); }

console.log(Counter()); // Count: 0
```

一个 hook、一个全局变量，值跨 render 留住了，setter 也能触发重渲染。再加一个 hook 就露馅：

```js
function Counter() {
  const [count, setCount] = useState(0);
  const [name, setName]   = useState('Alice');
  return `${name}: ${count}`;
}
```

第二次 `useState('Alice')` 进来时 `state` 已经是 `0`，初始化的那行直接跳过，返回的还是 `[0, setter]`。两个 hook 挤同一个槽位，互相覆盖。

这不是能打补丁的 bug。`One variable holds one value. Two hooks need two storage locations.` 一个变量装一个值，两个 hook 就得有两个位置，改法只剩一个：把变量换成列表，一个 hook 一个槽，按顺序填。这个改动看着很小，后面所有东西都是从它长出来的。

## 数组加游标，规则从这儿长出来

```js
let hooks = [];
let cursor = 0;

function useState(initialValue) {
  const index = cursor;
  hooks[index] = hooks[index] ?? initialValue;
  function setState(newValue) {
    hooks[index] = newValue;
    rerender();
  }
  cursor++;
  return [hooks[index], setState];
}

function rerender() {
  cursor = 0; // 每次渲染前归零
  console.log(Counter());
}
```

关键就是 `rerender()` 里那行 `cursor = 0`。数组跨 render 留着，游标每次从头开始，第一次调用永远拿 `hooks[0]`，第二次永远拿 `hooks[1]`。我在 `/tmp/mini_hooks.js` 里跑了三个 hook，输出 `render1: 1 b true | hooks.length = 3` 和 `render2: 2 B2 true | hooks.length = 3`，改过两个值，数组还是三个槽。

现在把第一个 hook 塞进条件里，跟着两帧走一遍：

```
Render 1 (someCondition = true):
  useState(0)       -> cursor 0 -> hooks[0] = 0       -> cursor: 1
  useState('Alice') -> cursor 1 -> hooks[1] = 'Alice'  -> cursor: 2

Render 2 (someCondition = false):
  useState('Alice') -> cursor 0 -> hooks[0] = 0       <- 读到了 count 的槽
```

第二次渲染里 `useState('Alice')` 落到游标 0，读出 `0` 而不是 `'Alice'`。Hook 没动，是游标不知道中间少了一次调用。我那份实现把第二个 hook 包进 `if (!skip)` 再跑，得到 `hooks = [10,"bee",true]` 变成 `hooks = [10,true]`，第三个 hook 顺位读到原本属于第二个的 `true`，不抛错，后面每一个都往前挪一格。DEV 下那句 `Rendered fewer hooks than expected` 是校验，不是机制；机制是位置对齐，少一次调用整排错位。母文里那句 `When a hook is skipped, every subsequent hook reads the wrong slot.` 我照抄了，循环和嵌套函数是同一个道理，只要两次 render 里调用次数可能不一样，游标就会漂。linter 不是在猜我写这段代码的意图，它守的是这套结构唯一能活的条件。

## dispatcher：为什么不能在组件外调

数组模型解释不了第二条规则。问题不在数组，在归属：`<Counter />` 和 `<UserProfile />` 不能共用一个全局 `hooks`，React 得在 Hook 被调用的那一刻知道该往哪个组件的存储里写。

解法是 dispatcher，一个只在 render 期间存在的全局对象，源码里是 `ReactSharedInternals.H`（母文引的是 `ReactSharedInternalsClient.js` 的 L61），初值 `null`。React 备了两套实现，首渲染一套、重渲染一套：

```js
const HooksDispatcherOnMount  = { useState: mountState,   /* useEffect: mountEffect, ... */ };
const HooksDispatcherOnUpdate = { useState: updateState,  /* useEffect: updateEffect, ... */ };

function renderWithHooks(Component, isFirstRender) {
  ReactSharedInternals.H = isFirstRender
    ? HooksDispatcherOnMount
    : HooksDispatcherOnUpdate;
  const result = Component();   // 组件在这里跑
  ReactSharedInternals.H = null; // 跑完立刻清空
  return result;
}
```

用户导入的那个 `useState` 只是去读 dispatcher，是 `null` 就抛 `Invalid hook call. Hooks can only be called inside a function component.`。母文有句我挺喜欢：`That error message isn't a React policy statement — it's a null check.` 报错不是在宣示政策，是没地方可写了。事件回调、`setTimeout`、模块顶层跑到这儿，render 早结束，门已经关上。

我手上这份 `packages/react-reconciler/src/ReactFiberHooks.js`（main 分支，175910 字节）行号和母文引的固定 commit 对不齐：他标 `renderWithHooks` 在 502 行、`HooksDispatcherOnMount` 在 3898 行，我这份是 505 行、562 到 566 行按 `current === null || current.memoizedState === null` 切 `ReactSharedInternals.H`，660 和 940 行渲染完换回 `ContextOnlyDispatcher`，那个对象里 `useCallback: throwInvalidHookError`。版本不同，行号本来就会漂，这种地方我一般按自己拉下来的那份记。两套 dispatcher 顺带解释了一件容易忽略的事：React 不用我传任何 flag 就知道这次该新建存储还是读旧存储，上下文是 dispatcher 带进来的。`BetaSu/big-react`（3899 star）的 `packages/react-reconciler/src/fiberHooks.ts` 把这段缩到一眼能读完，`renderWithHooks()` 先 `wip.memoizedState = null`，再按 `wip.alternate` 有没有值切 dispatcher，想对照着看比翻官方那 17 万字节省事。

## 真 React 用的是链表

数组模型教会的是逻辑，真实实现换了容器：每个组件的 fiber 上，`memoizedState` 指向该组件 Hook 链表的头，一次 Hook 调用对应一个节点。

```js
const hook = {
  memoizedState: null, // 当前值
  baseState: null,
  baseQueue: null,
  queue: null,         // setState 的更新队列
  next: null,          // 指向下一个 hook
};
```

首次渲染时 `mountWorkInProgressHook()` 建节点并接到 `currentlyRenderingFiber.memoizedState`（我这份 983 行建、996 行挂），重渲染时 `updateWorkInProgressHook()` 顺着 `next` 从头走（1004 行），按位置 clone 或复用节点。游标和 `next` 是同一个想法，机制不同，约束一模一样：Hook 每次 render 都得按同样的顺序出现。母文给的理由是 fiber tree 在 reconciliation 期间会动态挂载卸载，链表处理任意插删比数组自然，而遍历永远是「从头往前走」，跟重渲染的走法正好对上；这条我没在官方源码里找到明确说法，是那篇的判断，先记着。

`memoizedState` 里装什么按 Hook 类型变：`useState` 装当前值，`useEffect` 装带 callback 和 deps 的 effect 对象，`useRef` 装 `{ current }`。节点形状一样，内容不同。`7kms/react-illustration-series`（7909 star）的 `docs/main/hook-summary.md` 里 Hook 类型定义也是这五个字段，那份基于 React 17.0.2，别拿它当 19.x 的源码引用。

## 不给名字，是换来的

到这儿还差一句：为什么干脆不给状态起名字。Dan Abramov 2018-12-13 那篇《Why Do React Hooks Rely on Call Order?》专讲这个，他挨个代入八类替代 API，看各自怎么坏。我照着写了个 keyed 版，`/tmp/keyed_hooks.js`：

```js
const store = new Map();
function useStateKeyed(key, initial) {
  if (!store.has(key)) store.set(key, initial);
  return [store.get(key), v => { store.set(key, v); }];
}
function useWindowWidthKeyed() { return useStateKeyed('width', 800); }
```

组件调它两次、自己再有个 `width`，Node v22.22.2 打出来 `{"w1":800,"w2":800,"ownWidth":800}`；`setW1(1200)` 之后三个一起变 1200。换回数组游标版，同样三次调用是 `{"w1":800,"w2":800,"ownWidth":0,"len":3}`，改完只有 `w1` 变了。

状态全塞进一个对象，`useWindowWidth()` 这种带自己状态和 effect 的自定义 Hook 就抽不出来，Dan 把它列成 Flaw #1，原话是 `custom Hooks are largely the point of the proposal.` 传字符串 key 会撞名：我在自己的 Hook 里加一个状态，可能把用到它的组件全弄坏，而整条使用链我没法审计。Symbol 也躲不掉，同一个 Hook 调两次用的还是那个模块级 Symbol；两个上层 Hook 共用一个底层 Hook，菱形照样撞，他那句 `Function calls don't have a "diamond" problem because they form a tree.` 讲的就是函数调用排成树，每次调用各占一个位置。再补命名空间、工厂、组合 key，还是得靠 lint 保证 key 不重复，`But if we have to lint anyway, what problem did we solve?` 我抄下来了：linter 反正跑不掉，key 就是白背的负担，运行时还多一次 Map 查找。换来的东西挺实在，每次调用天然一个槽位、把组件里两行代码复制进自定义 Hook 是安全的、`const [id, setId] = useState(1)` 的 `id` 可以直接喂给 `useFriendStatus(id)`。顺序成了协议，代价是我不能在 `if` 里调 Hook。他那篇也没把话说满，`Hooks aren't perfect either, but it's the best tradeoff we could find for solving these problems.` 末尾提的并发和编译问题我没验证。

## 不占槽位的那个

React 19 的 `use()` 从反面印证。npm registry 上 react latest 是 19.3.1，官方 `react.dev/reference/react/use` 原句 `Despite its name, use is not a Hook. Unlike Hooks, it can be called inside loops and conditional statements like if.`。它能待在 `if` 里，因为压根不进那条链表，pending 时组件 suspend、最近的 `Suspense` boundary 显示 fallback；同一页还写了不能拿 `try/catch` 包它，内部就靠抛出来接上 Suspense。母文那句 `The rule doesn't bend. The architecture changes.` 用在这儿刚好：规则没松，是它不在规则管的那套结构里。

把四步摆一遍，一个全局变量、数组加游标、dispatcher、链表。规则就这么点东西：每个 Hook 在链表里按位置领一个槽，位置一改，它后面全坏。我现在往组件里加一个 Hook，脑子里出现的是 fiber 上多接了一个节点，从这次挂载起它就一直占着那个位置。

`/tmp/mini_hooks.js`、`/tmp/keyed_hooks.js` 和那份 175910 字节的 `ReactFiberHooks.js` 都留着。`FACT_POOL.md` 的 F22 记了今天找的文章地址和可借的骨架，F23 是 keyed 那组输出，F24 记了母本是谁。下回写 `useEffect` 那篇，从 1004 行 `updateWorkInProgressHook()` 往下翻，动笔前先去 GitHub 把讲 effect 链表的找出来。
