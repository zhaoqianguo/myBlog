上周我盯着一个计数器发呆。

组件里两个 `useState`，我在 `click` 回调里连着调两次 setter，渲染一次。把同一段代码搬进 `setTimeout`，还是渲染一次。

我以为自己已经懂 React 18 的自动批处理了。

然后我在两次 setter 中间塞了一行 `await null`。`click` 里变成两次，`setTimeout` 里还是一 次。

同一个 `await`，落在两个地方，结果不一样。我解释不了，所以花了一下午把它拆开。

## 先把数据摆出来

我在 `react@18.3.1` + `jsdom` 里搭了个最小页面，两个状态 `a`、`b`，每次渲染给计数器加一，跑完等两百毫秒再读数。

| 场景 | 渲染次数 |
| --- | --- |
| `click` 里同步连调两次 | 1 |
| `click` 里中间 `await null` | 2 |
| `click` 里中间空转 20 轮微任务 | 2 |
| `click` 里第二次放进 `queueMicrotask` | 2 |
| `click` 里中间 `await setTimeout(0)` | 2 |
| `setTimeout` 里同步连调两次 | 1 |
| `setTimeout` 里中间 `await null` | 1 |
| `setTimeout` 里中间空转 50 轮微任务 | 1 |
| `setTimeout` 里中间 `await setTimeout(0)` | 2 |

这张表里有两行互相打架。

如果批的是「同一个宏任务里的更新」，那 `setTimeout` 里 `await null` 之后仍然在同一个宏任务里，应该批住，对了；可 `click` 里 `await null` 之后也在同一个宏任务里，它却劈开了。宏任务这条说不通。

换「同一个微任务批次」试试。`click` 里一进 `queueMicrotask` 就劈开，看着像；但 `setTimeout` 里空转五十轮微任务照样批住。这条也不通。

边界不在时间上。它跟着调用点走。

## 更新带着一个优先级

`setState` 并不直接开始渲染。它先造一个 update 对象，挂到对应 fiber 的更新队列上，然后向调度器要一个 lane。

要 lane 的函数是 `requestUpdateLane`：

```js
function requestUpdateLane(fiber) {
  var mode = fiber.mode;
  if ((mode & ConcurrentMode) === NoMode) {
    return SyncLane;
  }
  // ...
  var eventLane = getCurrentEventPriority();
  return eventLane;
}
```

`getCurrentEventPriority` 只有四行，是整件事的关键：

```js
function getCurrentEventPriority() {
  var currentEvent = window.event;
  if (currentEvent === undefined) {
    return DefaultEventPriority;
  }
  return getEventPriority(currentEvent.type);
}
```

`window.event` 是浏览器在派发事件时挂上去的全局变量，指向当前正在处理的那个事件。它在事件回调的同步调用栈里有值，一离开就没了。

我打了个日志确认。`click` 回调开头 `window.event.type` 是 `click`，`await null` 之后立刻变成 `undefined`，再 await 两次还是 `undefined`，`setTimeout` 里自然是 `undefined`。

所以 `click` 里同步那两次，两次都拿到 `DiscreteEventPriority`，也就是 `SyncLane`，值为 1。`await` 之后的那一次，`window.event` 没了，落到 `DefaultEventPriority`，也就是 `DefaultLane`，值为 16。

1 和 16 不是一个 lane。

而 `setTimeout` 里的两次都是 `DefaultLane`，哪怕中间空转五十轮微任务，`window.event` 一直是 `undefined`，两次都是 16。

`await` 不是原因。它只是顺手把 `window.event` 弄没了。

## 所谓「合批」其实是没有排第二次活

知道两次更新落在同一个 lane，还没解释为什么只渲染一次。按理说挂了两条 update，跑两轮也说得通。

真身在这里，`ensureRootIsScheduled`：

```js
var newCallbackPriority = getHighestPriorityLane(nextLanes);
var existingCallbackPriority = root.callbackPriority;

if (existingCallbackPriority === newCallbackPriority) {
  // The priority hasn't changed. We can reuse the existing task. Exit.
  return;
}
```

第一次 `setState`：`root.callbackPriority` 还是空的，走下面去排一份活，把「有个 `SyncLane` 的活要干」记在 root 上。

第二次 `setState`：update 照样挂上 fiber，队列照样多一条，但走到这里发现「已经有一个同优先级的活在排队了」，直接 return，不再排第二份。

所以「批处理」这个词其实有点误导。React 没有把两个更新合并成一个，它只是没有排第二次活。等那份活真正执行的时候，fiber 的队列里躺着两条 update，一起算完。

状态不丢，是因为 update 早就入队了，跟排几次活无关。

这个设计省下的不只是一次渲染。它把「同一优先级的一串更新」变成了可以推迟、可以打断的一整块。后来 `startTransition` 能成立，靠的就是这个。

## 为什么 `click` 里第一个微任务就能读到新值

`SyncLane` 的调度走微任务：

```js
scheduleSyncCallback(performSyncWorkOnRoot.bind(null, root));
scheduleMicrotask(function () {
  if ((executionContext & (RenderContext | CommitContext)) === NoContext) {
    flushSyncCallbacks();
  }
});
```

回调一返回，微任务就把渲染干完了。所以我实测 `click` 里 `setA` 之后立刻读 DOM 还是旧值，第一个微任务之后就已经是新的。

`DefaultLane` 不走微任务，走 scheduler 的 `MessageChannel`，那是新开一个宏任务。我在 `setTimeout` 里 `setA` 之后连读三个微任务都是旧值，第四个挂的 `setTimeout(0)` 回调里才看到新值。

同样是「批住不刷」，两种 lane 把活交给的队列完全不同。这一点在写代码时几乎感觉不到，但在「改完状态立刻读 DOM」的场合是两种体验。

## React 17 完全是另一套

17 没有优先级这套东西，它用一个全局位：

```js
export function batchedUpdates(fn, a) {
  const prevExecutionContext = executionContext;
  executionContext |= BatchedContext;
  try {
    return fn(a);
  } finally {
    executionContext = prevExecutionContext;
    if (executionContext === NoContext) {
      resetRenderTimer();
      flushSyncCallbacksOnlyInLegacyMode();
    }
  }
}
```

合成事件外面套的是 `batchedEventUpdates`。位一挂上，`setState` 就不当场刷；函数返回、位复原，`finally` 里补一次 flush。

关键在「同步调用」这四个字。位只在 `fn` 的同步执行期间有效。`setTimeout` 里调 `setState` 时，外面那层早就返回了，位没了，于是每次都当场同步刷一遍。

我用 `react@17.0.2` 验了一遍：事件回调 1 次，`setTimeout` 2 次，`Promise.then` 2 次。

有意思的是，18 里还留着这条同步刷的分支：

```js
if (lane === SyncLane && executionContext === NoContext &&
    (fiber.mode & ConcurrentMode) === NoMode && !isBatchingLegacy) {
  resetRenderTimer();
  flushSyncCallbacksOnlyInLegacyMode();
}
```

条件是 `fiber.mode & ConcurrentMode` 为零。`ReactDOM.render` 建出来的树没有 `ConcurrentMode`，这条分支照旧生效。我在 18.3.1 里用 `ReactDOM.render` 试了，`setTimeout` 里还是 2 次，而且 `setA` 之后同步读 DOM 已经能读到新值；同样的代码换成 `createRoot` 是 1 次，同步读是旧的。

所以「React 18 自动批处理」这句话是跟着 `createRoot` 走的，不是跟着版本号走的。升级了 React 但没换 root API 的项目，行为其实一点没变。

## 两个会真出事的坑

第一个，值形式在队列里被覆盖：

```js
setCount(count + 1);
setCount(count + 1);
```

两条 update 都基于闭包里同一个 `count`，最后只加一。函数形式才对：

```js
setCount(c => c + 1);
setCount(c => c + 1);
```

我用 `count` 初始为 1 跑过：值形式最终 1，函数形式最终 3，两次都只渲染一次。这个坑在批处理下更隐蔽，因为不批的时候每行都会 re-render，中间值在界面上露一下，你至少能察觉。

第二个，`setTimeout` 里改完状态立刻读 DOM。批不批先不谈，`DefaultLane` 一定排在这一批微任务之后。真要同步读，只能 `flushSync`：

```js
flushSync(() => setCount(9));
```

我实测 `click` 里先 `setA(1)` 再 `flushSync(() => setB(2))`，渲染 3 次，`flushSync` 之后 DOM 是 `1/2`。拿三次渲染换一次确定的同步读，值不值看场景。

## 回到那个 await

它没有「打断批处理」。它只是让 `window.event` 变成 `undefined`，于是第二次 `setState` 领到了另一个 lane。

React 从 17 到 18 换的其实不是「批得更多了」。换的是「要不要批」这个判断的依据 —— 从「我现在是不是在某个同步上下文里」变成了「这次更新是什么优先级」。

前者是个布尔位，后者是个能排序的数值。有了后者，那套「这条更新可以慢一点」的划分才落得下来。我顺手试了 `startTransition`：`click` 里一个同步更新加一个 transition 里的更新，渲染 2 次；两个都包进 transition，渲染 1 次。

同一套机制，顺手就长出了并发渲染的地基。
