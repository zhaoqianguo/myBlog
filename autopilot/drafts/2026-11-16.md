`Promise` 和 `setTimeout` 谁先跑，这题我背过答案：微任务先。可真被追问一句「微任务到底在哪一步被清掉」，我就卡住了。背下来的答案是结论，不是机制。

于是我在 `node v22.22.1` 下写了几段代码，一段问一个问题，跑出来的东西比背的答案有用。

## 第一段：谁先谁后

```
console.log('1 sync start')
setTimeout(() => {
  console.log('4 timeout')
  Promise.resolve().then(() => console.log('5 micro in timeout'))
}, 0)
Promise.resolve().then(() => console.log('2 micro a'))
queueMicrotask(() => console.log('3 micro b'))
console.log('sync end')
```

```
1 sync start
sync end
2 micro a
3 micro b
4 timeout
5 micro in timeout
```

顺序本身没什么意外。有意思是第 5 行：`timeout` 这个回调里又挂了一个微任务，它没等到下一轮，紧跟着自己就跑了。也就是说微任务不是「排在所有定时器后面的一档」，它是贴着每一次回调尾巴走的东西。

## 第二段：清一遍还是清到空

这是我原来答不上来的那个点。猜「清一遍」的话，下面这段里的定时器应该能在链条中间插进去：

```
let fired = false
setTimeout(() => { fired = true; console.log('timeout fired') }, 0)

let i = 0
function spin() {
  if (i++ < 5) Promise.resolve().then(spin)
  else console.log('micro chain end, i =', i, 'timeout fired?', fired)
}
Promise.resolve().then(spin)
```

```
micro chain end, i = 6 timeout fired? false
timeout fired
```

链条一层层往里套了 5 次，定时器一次都没插进来。等链条自己走完，`fired` 还是 `false`。所以是「清到空」：每取出一个微任务执行，它新挂上去的微任务会被追加进同一个队列，队列空之前不出这一轮。

这条往下推一步就是件挺吓人的事。递归挂微任务，可以把定时器和渲染一直按在地上。Node 里我这么干，整个进程卡住，CPU 满转，`setTimeout` 的回调永远等不到。浏览器里等价的操作是把 `requestAnimationFrame` 饿死，页面直接不响应。别的异步写法都做不到这一点，只有微任务能，因为它清空的条件是「队列空」，而队列里有没有东西完全由你自己决定。

## 第三段：两个定时器之间

清空发生在哪，还有种问法：同一批定时器，A 的微任务会不会跑到 B 前面。

```
setTimeout(() => {
  console.log('A start')
  Promise.resolve().then(() => console.log('  A 的微任务'))
  console.log('A end')
}, 0)
setTimeout(() => {
  console.log('B start')
}, 0)
```

```
A start
A end
  A 的微任务
B start
```

会。A 的微任务插在 A 和 B 中间。要是一轮循环里排队的定时器很多，每个后面都清一次，这轮的总耗时就不是「所有回调之和」，而是「所有回调之和 + 每次清空的开销」。定时器回调里顺手挂几个 `.then` 的人不少，量起来的时候这块是能看见的。

## 第四段：`nextTick` 站在哪

Node 还有一条 `process.nextTick` 队列，跟 Promise 微任务不是同一条。

```
Promise.resolve().then(() => console.log('promise 1'))
process.nextTick(() => console.log('nextTick 1'))
Promise.resolve().then(() => console.log('promise 2'))
process.nextTick(() => {
  console.log('nextTick 2')
  process.nextTick(() => console.log('  nextTick 2.1'))
})
```

```
nextTick 1
nextTick 2
  nextTick 2.1
promise 1
promise 2
```

`nextTick` 整条队列先走完，才轮到 Promise。而且 `nextTick` 里套 `nextTick`，照样在后面立刻执行，不会掉到 Promise 后面去。两条队列各有各的清空时机，名次是固定的：`nextTick` 永远压一头。

这也是 `nextTick` 比 Promise 更容易把进程搞死的原因。它跑在更早的位置，饿死的东西更多。

## 第五段：I/O 和 immediate

前四段都在主线程同步代码和定时器上打转。真正干活的那两个阶段，规矩一样吗。

```
const { readFile } = require('fs')
readFile('/etc/hosts', () => {
  console.log('io A start')
  Promise.resolve().then(() => console.log('  A 的微任务'))
  console.log('io A end')
})
readFile('/etc/hosts', () => {
  console.log('io B start')
})
setImmediate(() => {
  console.log('immediate A start')
  Promise.resolve().then(() => console.log('  immediate A 的微任务'))
  console.log('immediate A end')
})
setImmediate(() => {
  console.log('immediate B start')
})
```

```
immediate A start
immediate A end
  immediate A 的微任务
immediate B start
io A start
io A end
  A 的微任务
io B start
```

两个阶段都是同样的形状：A 收尾、清空、再进 B。不是「一个阶段全跑完再统一清」，是每个回调跑完清一次。

这条对写库的人有实际影响。一个 `readFile` 回调里挂的 `.then`，会在下一个 `readFile` 回调之前跑完。想让一批 I/O 结果攒齐再处理，塞微任务不解决问题，它们在批与批之间就被清掉了；得用计数器或者 `Promise.all` 那种显式汇总。

## 第六段：`await` 站在哪一格

`async` / `await` 是语法糖，这我知道。但它糖化出来的东西排在微任务队列的哪个位置，我一直以为「跟 `.then` 差不多」。

```
async function f() {
  console.log('f start')
  await null
  console.log('f after await')
}
console.log('before')
f()
Promise.resolve().then(() => console.log('plain then 1'))
console.log('after calling f')
```

```
before
f start
after calling f
f after await
plain then 1
```

`f after await` 跑在了 `plain then 1` 前面。按理说 `f()` 调用在先，`await` 该排到后面去才对，结果是反的。

`await` 不是把剩下的代码挂到「当前队尾」，而是先把当时已经在排的都让过去，自己插到队首那一档。这条在只写一个 `.then` 的时候看不出来，多挂几个就露了。

同一个 `await`，接的东西不一样，代价也不一样。我拿三个函数试了一下，每个都在恢复时打一行：

```
async function nativeAwait() {
  await Promise.resolve()
  console.log('native await resumed')
}
async function thenableAwait() {
  await { then(r) { r() } }
  console.log('thenable await resumed')
}
async function plainAwait() {
  await 1
  console.log('plain await resumed')
}
nativeAwait(); thenableAwait(); plainAwait()
Promise.resolve().then(() => console.log('tick 1'))
Promise.resolve().then(() => console.log('tick 2'))
Promise.resolve().then(() => console.log('tick 3'))
Promise.resolve().then(() => console.log('tick 4'))
Promise.resolve().then(() => console.log('tick 5'))
```

```
native await resumed
plain await resumed
tick 1
tick 2
tick 3
tick 4
tick 5
thenable await resumed
```

前两个跟 `await 1` 是一个档位，都跑在五个 `tick` 前面。`await` 一个 thenable，直接掉到所有 `tick` 后头去了。

原因在 `await` 背后那一步：碰到 thenable 得先调它的 `then`，这本身要走一轮微任务；拿到结果之后恢复执行，又是一轮。普通值和原生 Promise 不用这一步。同样一行 `await`，写在 thenable 前面就多了一轮排队。

这解释了我以前遇到过的一件事：某个自己封装的「类 Promise」对象，放进 `await` 之后，紧跟着的那行 `console.log` 莫名其妙跑到了别处。当时以为是框架的锅，其实是那个对象身上有 `then`。

## 所以「在哪一步」

在调用栈变空的那一步。

不是事件循环转一圈，不是当前阶段结束，是每次回调的栈帧弹干净之后、返回值交给下一件事之前。清空的判据是队列为空，队列里有什么由回调自己决定，所以它既是「立刻执行」的保证，也是唯一能让进程饿死的口子。

回到开头那题。背「微任务先」能答对，但那句话只说了名次，没说出时机。补上「栈空即清、清到空为止」这半句，那些奇怪的输出才都能自己推出来。
