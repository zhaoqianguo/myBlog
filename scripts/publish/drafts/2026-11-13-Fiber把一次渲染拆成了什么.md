继上一篇《状态没有名字，React 却一次都没认错》后，我又往下翻了一层。那篇讲 Hook 链表挂在 fiber 的 `memoizedState` 上，fiber 当时只是个背景板，一句「每个组件对应一个 fiber」就带过去了。可要说清一次渲染凭什么能被拆开，躲不掉它。

我一直把 Fiber 当成虚拟 DOM 换了个名字，直到被问到「拆成什么」，才发现自己说不上来。

先从一个只有按钮和数字的小组件说起，把一次点击之后 React 要干的活摊开，再回头看 fiber 长什么样。

## 一次点击，React 要干多少活

摆一个最小得不能再小的应用：一个按钮，一个显示数字的 `span`，点一下按钮，数字加一。

```jsx
class ClickCounter extends React.Component {
  state = { count: 0 };
  handleClick = () => this.setState({ count: this.state.count + 1 });
  render() {
    return [
      <button onClick={this.handleClick}>Update counter</button>,
      <span>{this.state.count}</span>,
    ];
  }
}
```

点下去之后，React 手上排着这么一串活：把 `ClickCounter` 的 state 里的 `count` 改掉，重新取回 `render` 返回的两个子元素，跟上一轮那两个比一比 props 有没有变，把 `span` 的 props 更新成新的数字，顺带还要处理生命周期方法、更新 ref。这些活动在 Fiber 里被统一叫做 work，活的种类跟着元素类型走：类组件得先 new 出一个实例，函数组件不用，原生标签对应的是 DOM 的增删改，portal 又是另一套。JSX 编译完得到的不是 HTML，是一批带 `$$typeof`、`type`、`key`、`props` 的普通对象，文本内容是挂在 `span` 和 `button` 的 children 上，点击回调是 `button` 的 props 里的一项。

这串活分两拨人干：reconciler 负责算出新旧两棵树差在哪，renderer 负责把差的那部分真的落到目标上。浏览器里目标是 DOM，React Native 里是原生视图，两边共用一个 reconciler，各写各的 renderer。早年那句「虚拟 DOM」说的就是前半段，现在官方不太用这个词了，因为容易跟内部那棵可变树混起来。分成两阶段还有个更实际的用处，讲到可中断时会回来。

## 主线程只有那么点时间

一帧按 60Hz 的屏算，是 16.7 毫秒左右。这十几毫秒里浏览器还要做样式计算、布局、绘制、合成，还要响应输入，留给应用代码的更少。React 15 及以前的 reconciler 用递归对比新旧虚拟 DOM 树，一旦开始就一口气把整棵树比完才把主线程还回去。应用规模不受限制，组件层级一深，这趟递归就占住主线程不放，浏览器想画下一帧画不了，动画掉帧，点按钮也没反应，页面发涩。

那个年代的调用栈长这样：从 `renderRoot` 压一帧，往下一层组件再压一帧，一直压到最深的叶子，再一层层弹回来。栈帧里装着这一层的局部变量和「跑完该回哪儿」，可这副栈归运行时管，React 碰不到，没法在中间说「停在这儿，下一帧接着」，更没法把某一帧抽出来丢掉。所以老实现被叫作 Stack Reconciler，名字里的 Stack 就是指它拿调用栈记当前处理到哪个单元。

优化其实做了不少。协调算法复杂度是 O(n)，列表用 `key` 认人，只更新需要更新的节点，更新还做批量。可这几样减的是活的总量，减不掉「一口气占着主线程」这件事：哪怕只剩一半节点，还是得从头走到尾才能停。

问题不在算得多，在没地方停。

React 16 换了个做法：比较几个节点之后就问一次浏览器有没有更高优先级的事要办，有就主动让出主线程，等空闲了再接着比下几个，如此循环。记录当前处理单元的那个数据结构叫 fiber，新算法也就叫 Fiber Reconciler，和老的 Stack Reconciler 正好对上。这种把渲染工作摊到多帧的能力，后来叫时间分片。

浏览器其实给过一个现成的口子。`requestIdleCallback` 可以把一个函数排到空闲时段执行，回调里的 `deadline.timeRemaining()` 会告诉你这一帧还剩多少毫秒可用，`didTimeout` 为 `false` 就说明这段时间还没被用完，而且这个剩余值随时会变，浏览器一插进来别的活就得重新问。把这段回调贴进控制台跑，常见输出是 `49.9 false`，意思是还有 49.9 毫秒、没超时。可惜它触发得不够勤，等不到足够多的空闲帧，React 团队后来自己写了一套 scheduler 来排这些活。

有了空闲时间也只是解决了「什么时候做」，还缺「做多少」：得先把一整趟活切成能一份一份领走的单元，才能按剩余时间领几份、把剩下的留到下一帧。

## 把栈帧从运行时手里拿回来

讲 Fiber 架构的那份笔记里，把要补的能力列得很直白：暂停一份工作、待会儿再回来；给不同种类的活排优先级；复用之前算完的部分；一旦这份活被更新的数据顶掉了，直接中止。要做到这些，得先把活拆成单元，一个 fiber 就是一个工作单元。

那句定义说得干脆：Fiber 是对栈的一次重新实现，专门给 React 组件用的，一个 fiber 可以当成一个虚拟栈帧。

这话不是打比方。函数一调用就压一个栈帧，栈帧代表这个函数正在做的事，函数返回才能弹出来，整副栈归运行时管。把栈帧换成内存里一个普通对象，什么时候执行它、要不要复用、算到一半能不能扔，就都由 React 说了算。栈帧能留在内存里，也就能想什么时候执行、按什么顺序执行，这正是调度需要的前提。为了这件事，React 走的是 pull 的路子：数据来了不立刻算，等要用的时候再算，屏幕外的东西可以拖着，数据来得比帧率快可以合并，用户点击造成的动画更新可以压过刚从网络拿回来的内容。push 那一套得由写业务的人决定什么时候算，pull 则由框架自己判断哪些计算此刻是相关的。

要拆成单元，还得有个能停下来再找回来的遍历方式。递归不行，于是 React 换成了链表。

## 三个指针撑起一棵树

先说 fiber 节点的三层身份。作为架构，它取代了老协调器里的递归栈，这一层的变化就是 Stack Reconciler 变 Fiber Reconciler。作为静态数据结构，它对应一个 React element，`tag` 记着这是函数组件、类组件还是原生标签，`type` 是组件函数本身或者 DOM 标签名，`key` 用来在列表里认人，`stateNode` 指向真实的 DOM 节点或者类组件实例。作为动态工作单元，它记着这次更新带来的状态变化和要执行的操作：`pendingProps` 是刚传进来还没用的输入，`memoizedProps` 是上一轮算完记下的输入，`memoizedState` 是产出当前界面用的状态，`updateQueue` 排着状态更新、回调和 DOM 更新，`flags` 记这次要做的增删改，`lanes` 和 `childLanes` 管优先级。

顺带说一个容易看岔的地方：2018 年前后的源码里，记操作的字段叫 `effectTag`，优先级用的是 `expirationTime`；2020 年 5 月优先级模型换成 lane，字段也改叫 `flags`。贴着老字段的 FiberNode 定义和现在的对不上，是版本不同，不是另一套机制。

真正把节点连成树的只有三个指针：

```js
// FiberNode 里管树形关系的字段
this.return = null;   // 处理完要回到的节点
this.child = null;    // 第一个子节点
this.sibling = null;  // 右边第一个兄弟
this.index = 0;
this.alternate = null; // 另一次更新里对应的那个 fiber
```

`child` 指向组件 render 返回的那一个节点，`sibling` 把同一层剩下的孩子串成单向链表，`return` 指向处理完当前节点后该回去的地方。三个字段合起来，就把「往子树里钻一层」和「同一层挨个处理」两件事都表达出来了：每个节点只记自己往下的第一步和往右的一步，不必知道整棵树长什么样。

`return` 这个名字值得停一下。它没叫 `parent`，因为作为一个工作单元，重点是干完活往哪儿回，对应的是栈帧里的返回地址，不是家谱里的父亲。子节点和它的兄弟都收工了，才顺着它回到上层。这也正是为什么一个组件返回多个子元素时，它们会串成一条单向链表，表头挂在父节点的 `child` 上，每个孩子的 `return` 都指回同一个父亲。

拿一个具体例子画一遍。有个 `List` 组件，里面一个 button 和三个 `Item`，点一下按钮把每个 `Item` 里的数字平方。对应的 fiber 树从 `HostRoot` 起步，它是 React 内部建的特殊节点，充当最外层组件的父亲，`return` 是 `null`；往下 `child` 指到 `List`，`List` 的 `child` 指到 button，button 的 `sibling` 指到第一个 `Item`，三个 `Item` 依次用 `sibling` 串成一串，每个节点的 `return` 都指回自己上一层。用文字画出来大概是这个形状：

```
HostRoot
  └─ child → List
        └─ child → button
              └─ sibling → Item(0)
                    └─ sibling → Item(1)
                          └─ sibling → Item(2)
```

直线往下的是 `child`，横着串的是 `sibling`，往回的箭头是 `return`，图上没画出来，但每个节点都带着。从 `HostRoot` 出发，反复查当前节点的 `child`、`sibling`、`return`，构建或者更新对应的 fiber 节点，回到 `HostRoot` 时整棵树就走完了。这仍然是深度优先，只是走法从「函数调用自己」换成了「顺着指针挪」。

Stack Reconciler 用栈天然能找到子节点和父节点，Fiber 靠这三个指针达到同样的目的，还多拿到一样东西：走到哪儿，是可以记下来的。

## 走进去，走出来

遍历这件事由四个函数分担：`performUnitOfWork`、`beginWork`、`completeUnitOfWork`、`completeWork`。前两个负责「走进」一个组件，后两个负责「走出」它；真正干活的其实是 `beginWork` 和 `completeWork`，另外两个主要管迭代。这个说法很形象，begin 是 stepping into，complete 是 stepping out。

把开头那个 `ClickCounter` 摆进来。协调总是从最顶上的 `HostRoot` 开始，不过 React 会跳过已经处理过的节点，一路快进到还有活没干完的那个；比如在组件树很深的地方调了一次 `setState`，React 也是从顶上起，很快略过那些父节点，直奔调 `setState` 的组件。

简化的循环长这样：

```js
function workLoop() {
  while (nextUnitOfWork !== null) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
}

function performUnitOfWork(fiber) {
  const nextChild = beginWork(fiber);   // 返回下一个要处理的子节点，或 null
  if (nextChild !== null) return nextChild;
  return completeUnitOfWork(fiber);
}

function completeUnitOfWork(fiber) {
  while (true) {
    const returnFiber = fiber.return;
    const siblingFiber = fiber.sibling;
    completeWork(fiber);
    if (siblingFiber !== null) return siblingFiber;
    if (returnFiber === null) return null;
    fiber = returnFiber;
  }
}
```

`nextUnitOfWork` 存的是 workInProgress 树上那个还有活要干的节点，React 靠它判断还有没有别处没做完；当前 fiber 处理完，这个变量要么指向下一个节点，要么变成 `null`，变成 `null` 就退出循环，准备 commit。`beginWork` 总是返回下一个要处理的 child 或者 `null`：有 child 就把它交给 `nextUnitOfWork`，没有 child 说明这条分支到底了，可以完成当前节点。

完成也不是收一个就完。`completeUnitOfWork` 主体是一个大 while：完成当前 fiber 之后先看有没有兄弟，有就退出函数把兄弟交回去，让循环从这条新分支开始；没有兄弟就沿着 `return` 上移一层继续完成。有个细节容易记错：走到兄弟的时候，父节点还没完成，只有所有从子节点出发的分支都收了口，才轮到父节点完成并继续往上退。也正因为这样，React 应用副作用是从孩子往父亲走。

我把开头那棵小树按三个指针连起来，在 Node v22.22.2 上跑了一遍这个循环，屏幕上打出来的是两行：

```
begin   : App -> div -> i am -> span -> KaSong
complete: i am -> KaSong -> span -> div -> App
```

往下的顺序和递归版一模一样，往上收口却是叶子先来。文本 `i am` 没有子节点，立刻 `completeWork`；轮到 `span`，它得先等自己的 `KaSong` 收完口，所以 `KaSong` 排在 `span` 前面；`div` 又要等两个孩子都完事。我又让循环每处理两个单元就强制让出一次，让出的位置分别落在 `i am` 和 `KaSong` 上，回来接着走，两行顺序一点没乱。递归版做不到这件事，它的进度在栈里，取不出来。

`beginWork` 与 `completeWork` 里真正做了什么，可以按节点类型想：类组件要调生命周期、跑 `render` 拿子元素；原生标签要在 `completeWork` 里把 DOM 节点准备好、把 props 的差别记下来。四个函数名看着绕，其实只干了两件事，一层层进去，再一层层出来。

## 两棵树，一张草稿

到这里还差一块：既然能停下来，停下来的那份半成品放哪儿。

讲双缓存有个比方特别直观。用 canvas 画动画，每帧绘制前都要 `ctx.clearRect` 清掉上一帧；要是当前帧算得久，清屏到画完之间有一大段空隙，屏幕上就是白屏。解法是先在内存里把这一帧画好，画完直接整帧替换，省掉两帧之间的计算时间，也就不会闪。这种「在内存中构建并直接替换」叫双缓存，React 拿它来构建和替换 Fiber 树，对应的正是 DOM 树的创建与更新。

React 里同时最多有两棵 Fiber 树：屏幕上当前显示的那棵叫 `current`，正在内存里构建的那棵叫 `workInProgress`。两棵树上对应的节点用 `alternate` 互相指着：

```js
currentFiber.alternate === workInProgressFiber;
workInProgressFiber.alternate === currentFiber;
```

所有工作都做在 `workInProgress` 的节点上。render 阶段一边走过 `current` 树，一边用 `render` 返回的新数据造出对应的另一半，攒成一棵等着刷上屏的树。这棵树上改了什么、打了什么标记，用户一点都看不见，有人管它叫 draft，草稿；正因为有草稿，React 才能先把所有组件都算完，再一次性把变更刷到屏幕上。React 有条核心原则是一致性，DOM 永远一口气更新，不给用户看半截结果。

换树靠的是应用根节点上的一个指针。`ReactDOM.render` 首次执行会建出 `fiberRootNode` 和 `rootFiber`：前者是整个应用的根，只有一个，后者是这次组件树的根，一个应用里可以多次 render 不同的树，于是会有多个 `rootFiber`。`fiberRootNode.current` 指着当前页面上内容对应的那棵树。首屏时页面还没挂任何 DOM，`current` 指着的 `rootFiber` 一个子节点都没有，整棵 current 树是空的；render 阶段按 JSX 在内存里逐个造出 Fiber 节点连成 `workInProgress` 树，commit 阶段渲染上屏，随后 `fiberRootNode.current` 拨过去，草稿就成了正本。

更新时同样走一遍。点一下那个 `<p>` 让 `num` 加一，就开一次新的 render 阶段，再建一棵 `workInProgress` 树；这回能从 `current` 树复用不少旧节点的属性，判断哪些能复用、哪些得重建，就是 Diff 算法。树建完进 commit，渲染完，`workInProgress` 变成新的 `current`。两张纸一直都在，只是身份对调，省下分配内存和垃圾回收的开销。

这也解释了为什么「暂停」常常不是等会儿接着算，而是整个丢掉重来：更高优先级的更新插进来时，正在算的那棵 `workInProgress` 可以不要了，从没被动过的 `current` 重新克隆一份开算，`pendingProps` 和 `memoizedProps` 一样的部分还能直接复用。屏幕上从头到尾都是完整的一帧。

## 一张只记改动的小清单

render 阶段算完，交出去的不是整棵树，是一条只串着「有事的节点」的线性表。

改 DOM、调生命周期、动 ref，这些都不算「用 state 和 props 算出界面」，在 React 里被叫做副作用。每个 fiber 节点都可以挂着副作用，编码在 `flags` 里，旧版叫 `effectTag`：原生标签的活是增删改元素，类组件可能要更新 ref、调 `componentDidMount` 和 `componentDidUpdate`。要快速找到它们，React 另建一条线性链表把这些节点串起来，用 `nextEffect` 相连、`firstEffect` 指到表头，遍历一条线比遍历一棵树快，也不用在没有副作用的节点上浪费时间。

有个很妙的比方：把它想成一棵圣诞树，用一串彩灯把所有带效果的节点连起来，灯串就是那条链表。举个例子，某次更新让 `c2` 被插进 DOM、`d2` 和 `c1` 改了属性、`b2` 要触发一个生命周期方法，链表就把这四个串起来，其余节点全跳过。应用这些效果是从孩子往父亲走，跟前面 `completeWork` 收口的顺序对得上。

新版源码里这条链的做法变了，`firstEffect`、`nextEffect`、`lastEffect` 已经不在 `FiberNode` 上，改成 `subtreeFlags` 一路往上冒泡，让父节点知道子树里有没有活。目的没变：先算清要改哪些，再找一条最短的路把它们执行掉。

## 能断的只有前半段

把两阶段摆回来看，可中断的是 render，不是 commit。

render 阶段只算不动：读 props、跑组件、比对新旧子元素、把要删要插要改的记成标记，全程在内存里，页面上什么都没发生。所以算到一半来了更高优先级的更新，这段工作可以直接丢掉，用户看不见；等主线程空下来，从 `current` 重新克隆一份接着算就行。也正因为随时能作废，React 才敢把整棵树拆成一个个单元慢慢领，还敢给不同的更新排优先级，动画更新压过刚从网络拿回来的内容。

这件事还有个连带后果。16.3 起，一批在 render 阶段跑的老生命周期方法被标上 `UNSAFE_`：`componentWillMount`、`componentWillReceiveProps`、`componentWillUpdate`。render 阶段可能被打断、重来、丢弃，往这些钩子里塞副作用就会执行得不受控；17.0 里不带前缀的版本被去掉了。留在 commit 阶段的 `getSnapshotBeforeUpdate`、`componentDidMount`、`componentDidUpdate`、`componentWillUnmount` 没有这个顾虑，那一段是同步的，可以放心碰 DOM。

commit 阶段不一样。这一步真的在动 DOM，做一半停下来，用户看到的就是半个界面，所以它没有 `shouldYield()`，进了就得一口气走到底。而且它自己还分两遍：第一遍把 DOM 的插入、更新、删除和 ref 卸载全做完，然后把 `finishedWork` 树指派给 `FiberRoot`，让 `workInProgress` 变成 `current`；第二遍才调剩下的生命周期和 ref 回调。换指针的时机卡在两遍之间，是为了让 `componentWillUnmount` 里看到的还是旧树，而 `componentDidMount`、`componentDidUpdate` 里看到的已经是新树。分两遍还保证整棵树的增删改都落实了，才去跑那些回调。

调度那一侧的门槛也写死在源码里。同步的循环是 `while (workInProgress !== null)`，一路做到底，点击、输入这类交互更新走它；并发的循环每做完一个单元问一次 `shouldYield()`，调度器说让就退出，退出时不用保存现场，`workInProgress` 还指着下一个节点，下一帧接着跑。另有一条按时间片收口的写法 `yieldAfter = now() + (nonIdle ? 25 : 5)`：非 idle 的更新攒够 25 毫秒让一次，idle 的 5 毫秒就让。注释里特意说明，这么做的目的不是省掉让出那点开销，而是故意把动画压到 30 帧，别让一大段渲染把主线程上的动画饿死。这种数字光看架构图是猜不出来的。

把一次更新切成两段，代价是内存里多养一棵树、每轮更新要维护 `current` 与 `workInProgress` 的对应关系，换来的是前半段可以随便打断、重排、丢弃，后半段短到不值得拆。我觉得这个取舍比「异步可中断」四个字实在得多，它讲清楚了代价落在哪一侧。

树收口到根之后，攒下的清单交给 commit，根指针从 `current` 换到 `workInProgress`，两棵树调换身份，下一轮更新又从 `alternate` 开始复用。上次看 `completeUnitOfWork` 里那句 `completedWork = returnFiber` 我还觉得普通，现在再看，它就是在手动弹栈。
