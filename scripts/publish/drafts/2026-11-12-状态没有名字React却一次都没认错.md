用了几年 `useState`，要我说清它凭什么记得住上一次的值，一开始是答不上来的。

规则倒是背得熟：只在顶层调用，只在 React 函数组件或自定义 Hook 里调用。`eslint-plugin-react-hooks` 会在代码跑起来之前把违规标红。可要问为什么，得到的答案通常是「因为 React 靠调用顺序认状态」，这话不算错，但它只是把问题复述了一遍。

顺序不是谁规定出来的，是被存储结构逼出来的。把 `useState` 从零搭一遍，两条规则会自己长出来。

## 一个变量装不下两个状态

`useState` 最少得做三件事：存一个值、把值返回、给个改值的入口。

```js
let state;

function useState(initialValue) {
  state = state ?? initialValue;
  function setState(next) {
    state = next;
    rerender();
  }
  return [state, setState];
}

function Counter() {
  const [count] = useState(0);
  return `Count: ${count}`;
}
```

一个组件、一个 Hook 时它没毛病：值存放在组件外面，跨 render 留得住，setter 还能触发重渲染。再加一个 Hook 就穿帮：

```js
function Counter() {
  const [count] = useState(0);
  const [name]  = useState('Alice');
  return `${name}: ${count}`;
}
```

第二次 `useState('Alice')` 进来时 `state` 已经是 `0`，初始化那行被跳过，两个 Hook 一起返回 `[0, setter]`，互相覆盖。

这不是能打补丁的 bug，是位置不够：一个变量只装一个值，两个 Hook 就得有两个位置。Rudi Yardley 那篇《React Hooks: not magic, just arrays》给的极简模型干脆用了两个数组，一个放值，一个放 setter，再用一个游标把两者对上：

```js
let state = [];
let setters = [];
let firstRun = true;
let cursor = 0;

function createSetter(cursor) {
  return newVal => { state[cursor] = newVal; };
}

function useState(initVal) {
  if (firstRun) {
    state.push(initVal);
    setters.push(createSetter(cursor));
  }
  const setter = setters[cursor];
  const value = state[cursor];
  cursor++;
  return [value, setter];
}
```

`createSetter(cursor)` 值得多看一眼：每个 setter 记住的是自己出生时的下标，所以点击按钮改的只是自己那一格，不会碰别人。渲染函数每次开头把 `cursor` 归零，`state` 数组留着不清空，第一次调用永远读第 0 格，第二次读第 1 格。模型里的 `firstRun` 经不起多个组件，真 React 当然不这么写；我把它记成一句话：状态的身份来自位置，不是来自变量名。

## 顺序一改，后面全串

关键就是那句 `cursor = 0`。数组跨 render 保留，游标每次从头开始，于是插槽的身份完全由「这是第几次调用」决定。我照着这个模型跑了一遍，三个 Hook、两次渲染都是三格，中间改过值也只是对应格子变。

现在把第一个 Hook 塞进 `if`，跟着两帧走一遍：

```
Render 1 (someCondition = true):
  useState(0)       -> cursor 0 -> state[0] = 0
  useState('Alice') -> cursor 1 -> state[1] = 'Alice'

Render 2 (someCondition = false):
  useState('Alice') -> cursor 0 -> state[0] = 0   <- 读到了 count 的格子
```

Hook 本身没动，是游标不知道中间少了一次调用。少一个，后面每一个都往前挪一格，而且不抛错，只是安静地读到别人的值。Rudi 那篇文章里更直观的一版是第二次渲染时 `firstName` 和 `lastName` 一起变成 "Rudi"。开发模式下 React 会抛 `Rendered fewer hooks than expected`，那是校验，不是机制；机制是位置对齐。

所以「不能在循环、条件、嵌套函数里调 Hook」不是口味上的规定。循环次数会变，条件分支会变，嵌套函数可能这帧调、下帧不调，只要两次 render 里调用次数可能不同，游标就会漂。linter 不是在猜你写这段代码时的意图，它守的是这套结构唯一能活下来的条件。

## 谁的状态：dispatcher 只在渲染时开门

数组模型解释不了第二条规则。问题不在数组，在归属：`<Counter />` 和 `<UserProfile />` 不能共用同一个全局 `state`，React 得在 Hook 被调用的那一刻，知道该往哪个组件的存储里写。

做法是 dispatcher，一个只在 render 期间存在的全局对象，源码里是 `ReactSharedInternals.H`，初值 `null`。React 备了两套实现，首次挂载一套、重渲染一套：

```js
const HooksDispatcherOnMount  = { useState: mountState,   /* useEffect: mountEffect, ... */ };
const HooksDispatcherOnUpdate = { useState: updateState,  /* useEffect: updateEffect, ... */ };

function renderWithHooks(Component, isFirstRender) {
  ReactSharedInternals.H = isFirstRender
    ? HooksDispatcherOnMount
    : HooksDispatcherOnUpdate;
  const result = Component();        // 组件在这里跑
  ReactSharedInternals.H = null;     // 跑完立刻关门
  return result;
}
```

从 `react` 里 import 的那个 `useState`，本体只是去读 `H`，读到 `null` 就抛 `Invalid hook call. Hooks can only be called inside of the body of a function component.`。这句报错看着像政策宣示，其实是一次空值检查：render 已经结束，门关了，没有组件存储可写。事件回调、`setTimeout`、模块顶层跑到这儿都一样。

两套 dispatcher 还顺带解释了一件容易忽略的事：React 不用你传任何 flag 就知道这次该新建槽位还是读旧槽位，上下文是 dispatcher 带进来的。卡颂《极简 Hooks 实现》里那个不到 100 行的版本为了省事，用 `isMount` 这个布尔变量扮演同样的角色；他在文末专门列了与真 React 的区别，第一条就是真 React 没有这个变量，而是不同时机换不同的 dispatcher，mount 时的 `useState` 和 update 时的 `useState` 根本不是同一个函数。这一句正好把模型和源码接上。

## 真 React 用的是链表

数组是讲逻辑用的模型，真实实现换了容器：每个组件对应的 fiber 上，`memoizedState` 指向这个组件 Hook 链表的头，一次 Hook 调用就是一个节点。

```js
hook = {
  memoizedState: null, // 当前状态
  baseState: null,     // 基状态
  baseQueue: null,     // 基队列
  queue: null,         // setState 产生的更新队列
  next: null,          // 指向下一个 Hook
};
```

卡颂的极简版把结构砍到三四个字段，更好读：`fiber.memoizedState` 存这条链表，`hook.queue.pending` 存这个 Hook 自己的更新，`hook.next` 串下一个 Hook。每次 `setState` 并不当场改值，只是往 `queue.pending` 里挂一个 `update`；这些 `update` 组成环状单向链表，`pending` 始终指向最后插入的那个，于是 `pending.next` 就是第一个。render 时从 `baseState` 出发，顺着环把 action 依次跑一遍，结果写回 `memoizedState`。连续点三次按钮，就是三个 `update` 排成一圈，一次算完。

要认领自己那一格，靠的是 `workInProgressHook` 指针：render 前把它拨回链表头，每遇到一次 `useState` 就往后挪一格。他那句结论说得很干脆：只要每次组件 render 时 `useState` 的调用顺序及数量保持一致，就总能通过 `workInProgressHook` 找到当前 `useState` 对应的 `hook` 对象。游标和 `next` 是同一个想法，容器不同，约束一模一样。

官方源码里首渲染走 `mountWorkInProgressHook()` 建节点并挂到 fiber 上，重渲染走 `updateWorkInProgressHook()` 顺着 `next` 从头走、按位置复用或 clone 节点；fiber 树更新时，把 `current.memoizedState` 链表上的 Hook 按顺序克隆到 `workInProgress.memoizedState`，这就是状态跨渲染还在的原因。节点形状统一，装什么按 Hook 类型变：`useState` 装当前值，`useRef` 装 `{ current }`，`useEffect` 装一个带 `create`、`destroy`、`deps` 的 effect 对象，同时给 fiber 打上 `flags`，等 commit 阶段处理。三条链别混在一起：Hook 是无环单向链表，`update` 和 `effect` 各是环状链表，一个管状态，一个管副作用。

## 干脆不给状态起名字

到这儿还绕不开一个问题：既然顺序这么娇气，为什么不给每个状态一个 key？写成 `useState('count', 0)` 看着多稳。

Dan Abramov 2018 年底那篇《Why Do React Hooks Rely on Call Order?》专门回答这个。他把社区提过的替代 API 挨个代入，从 Flaw #1 数到 #8，看各自怎么坏。归纳下来，卡在几个绕不过去的地方：

**自定义 Hook 先没了。** 如果规定一个组件只能调一次 `useState`、状态全塞进一个对象，那 `useWindowWidth()` 这种自己带状态和副作用的 Hook 就抽不出来。他说，自定义 Hook 基本就是这个提案的重点。

**key 会撞。** 同一个组件里写两个 `'name'` 是低级错误，真正麻烦的是你在自定义 Hook 里新增一个 state，可能把间接用到它的组件全弄坏，而整条使用链你没法审计。代码今天看着优雅，改起来特别脆。

**换 Symbol 也躲不掉。** `useFormInput()` 内部用的是模块级那个 `valueKey`，调两次就等于两次 `useState(valueKey)`，照样撞。两个上层 Hook 共用同一个底层 Hook 时还会撞上菱形问题；函数调用排成的是树，所以不会有菱形，每次调用天然各占一个位置。

**到头来还是得 lint。** 加命名空间、搞工厂函数 `createUseFormInput()`、层层组合 key，都能缓解，代价是每个自定义 Hook 都要先「实例化」且只能用一次，把组件里两行代码复制进自定义 Hook 也不再安全。他最不讨厌的方案是组合 key，可自己紧接着反问：既然还得靠 lint 保证 key 不乱传，那 key 到底解决了什么？运行时多一次 Map 查找，包体积多一堆字符串，都是白背的负担。

**值不好在 Hook 之间传。** `const [id] = useState(1)` 后面直接 `useFriendStatus(id)`，中间还能插一个 `useMemo`，是因为调用就写在函数体里。一旦把 Hook 初始化塞进默认参数、装饰器或工厂，输入输出得靠约定对上，effect 也没法用闭包捕获这些值。

按顺序领槽，恰好把这些一起绕开：每次调用天然一个槽位，两个 Hook 都把变量叫 `name` 也互不干扰，把组件里的两行复制进自定义 Hook 是安全的，Hook 之间传值就是普通的函数调用。代价写在明面上：条件里不能调，位置一改后面全坏。他也没把话说满，结尾留了一句，Hooks 并不完美，但这是当时能找到的最好取舍。

撞名不是纸面风险，跑一下就能看见。写个 keyed 版：

```js
const store = new Map();
function useStateKeyed(key, initial) {
  if (!store.has(key)) store.set(key, initial);
  return [store.get(key), v => { store.set(key, v); }];
}
function useWindowWidth() { return useStateKeyed('width', 800); }
```

组件里调两次 `useWindowWidth()`，自己再有一个 `width`，三个变量其实读同一格：`{"w1":800,"w2":800,"ownWidth":800}`；把 `w1` 改成 1200，三个一起变。换回数组游标版，同样三次调用占三格 `{"w1":800,"w2":800,"ownWidth":0,"len":3}`，改完只有 `w1` 动。名字听着稳，其实是把隔离的责任交给了人。

## 例外：use 不在链表里

React 19 的 `use()` 从反面又印证了一次。官方文档明说它名字带 `use` 但不是 Hook，可以放在 `if` 和循环里；因为它压根不进那条链表，pending 时靠抛出让最近的 `Suspense` 接住，所以同一页还特意写了别用 `try/catch` 包它。规则没松，是它不在规则管的那套结构里。

把四步连起来：一个全局变量装不下两个状态，于是换成数组加游标，一个 Hook 一格；dispatcher 决定这一格属于哪个组件、这次是新建还是读取；真 React 用 fiber 上的 Hook 链表做同样的事，只是把游标换成了 `next`。两条规则就是这套结构的边界：每个 Hook 按位置领一个槽，位置一改，它后面全坏。

我现在往组件里加一个 Hook，脑子里出现的不再是「又多了一个状态变量」，而是 fiber 那条链表的尾部多接了一个节点，从这次挂载起，它就一直占着那个位置。
