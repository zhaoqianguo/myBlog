一段混着 `Promise.then`、`queueMicrotask`、`process.nextTick` 和 `setTimeout(…, 0)` 的脚本，打印顺序我以前总也背不下来。知道 Promise 比定时器早，知道 nextTick 还要更早，可要说清「早在哪一步」，就说不上来了。

问题不在谁快谁慢，而在「清空」这个动作被安放在哪儿。

这次想把那个位置找出来。先把一段最小脚本摆出来，凭直觉猜一遍顺序：

```js
console.log('script start');

setTimeout(() => console.log('setTimeout'), 0);

Promise.resolve()
  .then(() => console.log('promise1'))
  .then(() => console.log('promise2'));

console.log('script end');
```

正确输出是 `script start`、`script end`、`promise1`、`promise2`、`setTimeout`。两个 `then` 排在定时器前面，哪怕定时器写的是 0 毫秒。

我以前一直把这解释成「微任务优先级高」。这话不算错，可它把一件位置固定的事说成了抢跑，往下再问一句「什么时候清、清到什么程度」，就答不出来了。顺序背后是两套完全不同的排队方式，得分开看。

## 一次任务，和一条排到空的队列

每个线程有自己的事件循环，它一圈一圈地转，每圈从任务队列里取出一个任务来跑。任务不只一条来源：脚本开始执行、事件派发、定时器到期、HTML 解析器把字节切成 token，都算任务；同源的几个窗口还共用一个事件循环，浏览器每圈有权挑从哪条来源取，好让点击、输入这类对延迟敏感的任务先走。任务内部按顺序执行，浏览器可以在两个任务之间插进渲染。

`setTimeout(fn, 0)` 里的 0 从来不是「立刻」。它只给定时器设了个门槛，到点之后把回调排成一个新任务；眼下这段脚本还在跑，它属于当前这个任务，`script end` 也就必然先于 `setTimeout` 打出来。决定顺序的不是那个数字，是「新任务要等到下一圈」。

微任务是另一回事。它用来放那些本该紧接当前这段脚本发生的事：把一批改动一起回应掉，或者让某段代码异步一点，却不想付出一整个新任务的代价。现行 HTML 规范说得很直白：微任务队列不是任务队列，微任务只是「通过 queue a microtask 算法创建出来的任务」的一个俗称。事件循环挑下一圈任务时，压根不会去挑它。

为什么要单列这么一类，不统统排成任务就好？把 Promise 回调当成新任务是最省事的写法，可那样一来，Promise 敲定时排队的那些回调得跟别的任务来源一起等浏览器挑圈，可能被任务之间才做的渲染白白拖后，也可能因为那一圈先照顾了用户输入而变得不确定；更麻烦的是跟别的 API 的时序对不上。规范给 Promise 留的口子是 `HostEnqueuePromiseJob`，把这类作业直接排进微任务队列，对一个已经敲定的 Promise 调 `.then` 也会立刻排一个微任务，这样即便状态早就定了，回调仍旧是异步的。有个实在的反面例子：IndexedDB 派发 success 事件之后，事务对象在派发结束那一步就转成 inactive，如果外面包的 Promise 回调没能在同一个任务里跑完，等它执行时事务已经关了，整个封装库就白写了。把回调压在当前任务结束之前，是这些 API 能成立的前提，不是谁为了快做的优化。

顺着这个理由往下看，微任务被设计成「紧接当前脚本」，其实是为了让一连串 Promise 回调在同一圈里连着跑完，中间不留给渲染和其他任务来源插队的机会。代价也落在同一处：这条队列一旦开始清，就得清到底。

可「当前脚本结束」到底是哪一瞬，还得看执行栈。

## 检查点插在哪一步

要先说清「栈空」。一段 JavaScript 跑起来，就有一个执行上下文压在栈上；每调一个函数再压一个新的，函数返回才弹掉；递归调自己也是一层一层压，压得越深占的内存越多。只有栈里一个上下文都不剩，运行时才认为眼下没有 JavaScript 正在执行，这时候才轮到排队的微任务。

规范里那一圈处理模型写得很朴素：从任务队列里挑一个可运行的任务，把事件循环的 `currently running task` 设成它，跑完它的步骤，再把这个字段设回 null，紧接着执行一次 `perform a microtask checkpoint`。检查点不是挂在这一圈开头，是紧跟在每个任务的步骤跑完之后。前面那段最小脚本里，`script start` 到 `script end` 属于同一个任务，任务一结束就做检查点，两个 `then` 因此赶在下一圈的定时器之前。

这个检查点自身是个 while 循环。事件循环上有个 `performing a microtask checkpoint` 的布尔标记，进来先看看是不是已经在清了，是就直接返回，防止重入；否则把标记置上，只要微任务队列不空，就取出最老的一个来跑，跑完接着取，直到队列真的空了，再把标记清掉。执行期间新排进来的微任务加在队尾，同样在这一轮里被取走，不会留到下一圈。前面那个链式 `.then` 就是这么连着打出来的：`promise1` 的回调跑完又排了 `promise2`，检查点没停，一起清掉。

顺序读起来规整，可一旦把事件派发掺进来，「栈空」这两个字的分量才显出来。

给内外两层 div 各挂一个点击监听，监听里同时放一个 `setTimeout`、一个 `Promise.resolve().then` 和一次属性修改，再让 MutationObserver 盯着属性。真实用户点一下内层，事件从内层冒到外层，规范认定的顺序是 `click`、`promise`、`mutate`、`click`、`promise`、`mutate`、`timeout`、`timeout`。每个监听回调返回时栈就空了，微任务队列当场清一次，所以两个监听之间会插进一组 `promise` 和 `mutate`；定时器各自排成新任务，排在后面。

换成脚本里直接调 `inner.click()`，顺序变成 `click`、`click`、`promise`、`mutate`、`promise`、`timeout`、`timeout`。事件是同步派发的，调用 `.click()` 的那段脚本还压在栈上，两个监听之间根本没有「栈空」这一瞬，微任务不能打断正在执行的 JavaScript，只能等两个监听都结束再一起清。同一次属性修改只留一条 `mutate`，也是这个原因。

所以这一步的位置既不是脚本文件的末尾，也不是定时器该跑的时候，而是当前这段 JavaScript 的执行栈清空的那一刻。任务结束时要清，回调返回、栈空了也要清；只要栈里还有东西，谁都插不进来。

## Node 把这一步拆成了两个队列

浏览器这边只有一条微任务队列要操心，Node 多了一条自己的。

Node 启动后先跑完交进来的脚本，再进事件循环，循环按阶段走：timers 跑 `setTimeout` 和 `setInterval` 到期的回调，pending callbacks 处理上一轮推迟的 I/O 回调，idle 和 prepare 只在内部用，poll 取回新的 I/O 事件并执行对应回调，check 跑 `setImmediate`，close callbacks 处理 `socket.on('close')` 这类。每个阶段有自己的 FIFO 队列，进去之后一直执行到队列空或者触到系统相关的上限，才挪到下一阶段。libuv 从 1.45.0 起把 timers 挪到 poll 之后每轮再跑一次，为了兼容，进入事件循环之前仍会先跑一次 timers；所以顶层脚本里 `setTimeout(…, 0)` 和 `setImmediate()` 谁先谁后并不保证，这点官方文档专门提了。

那张阶段图里没有 `process.nextTick`，官方文档的说法是它在技术上就不属于事件循环。运行时每次从底层处理完、回调进 JavaScript，算一次 operation；这个 operation 一结束，传给 `process.nextTick` 的回调就会在事件循环继续往下走之前被全部处理掉，跟当前处在哪个阶段无关。文档用 tick 称呼这种从底层切回 JS 的一次边界，也直说了这么做的两个用处：让用户有机会在事件循环继续之前处理错误、清掉不再需要的资源，或者重试一次；还有一种是让回调在调用栈展开之后、事件循环继续之前跑。

后一个用处有个很典型的小例子。继承 `EventEmitter`、在构造函数里直接 `this.emit('event')`，外面 `new` 完才挂 `on('event', ...)`，事件就丢了，因为发射的时候监听还没挂上。把发射塞进 `process.nextTick`，等构造函数返回、脚本把监听挂好之后再发，顺序就对了：

```js
const EventEmitter = require('node:events');

class MyEmitter extends EventEmitter {
  constructor() {
    super();
    process.nextTick(() => {
      this.emit('event');
    });
  }
}

const myEmitter = new MyEmitter();
myEmitter.on('event', () => {
  console.log('an event occurred!');
});
```

`queueMicrotask` 和 `Promise.then` 走的是另一条队列。翻 `nodejs/node` 的 `lib/internal/process/task_queues.js` 能对上：`nextTick()` 把回调包成 `TickObject` 塞进一个 `FixedQueue`，队列空时顺手把 `tickInfo` 上的 `kHasTickScheduled` 标记置起来；`queueMicrotask()` 走的是 `enqueueMicrotask(...)`，没有 AsyncLocalStorage 在用时直接走快路径入队。两条队列从入队那一步就分开了，谁也不往谁里面放。

真正决定先后的是 `setupTaskQueue()` 里那句 `setTickCallback(processTicksAndRejections)`，注释写着这是每个 tick 都要跑的回调。`processTicksAndRejections()` 是个 do/while：里层 `while ((tock = queue.shift()) !== null)` 把 nextTick 队列从头到尾取空，一个一个执行；取完了才调 `runMicrotasks()`，把引擎自带的微任务队列清一遍；然后看循环条件，如果这期间微任务又排了新的 nextTick，`queue` 重新不空，就再来一轮。写成伪代码差不多是这样：

```js
do {
  while ((tock = queue.shift()) !== null) {
    // 执行这条 nextTick 回调
  }
  runMicrotasks();
} while (!queue.isEmpty() ||
         (hasRejectionToWarn() && processPromiseRejections()));
```

这段结构把「nextTick 为什么整体排在 Promise 前面」讲得很干净：不是给 nextTick 设了个更高的优先级数字，而是清空的动作被拆成先后两步，先把自己那条队列取空，再去碰微任务队列。反过来，微任务里排的 nextTick 也不会掉到下一圈事件循环，它在同一轮的第二次 do/while 里就被补掉了。我认为这比「nextTick 比 Promise 快」这类说法更值得记住，因为它顺带说清了代价落在哪一侧：nextTick 排在事件循环所有阶段之前，递归地 `process.nextTick` 能让循环永远走不到 poll，官方文档把这种把 I/O 饿死的写法单独拎出来警告过。

`queueMicrotask()` 是后来才补上的公开入口。微任务队列早就在，只是以前只在内部拿来驱动 Promise，想手动排一个微任务，得借一个已经敲定的 Promise，或者绕到 MutationObserver 上；各运行时、各浏览器的做法不一样，顺序就难保证。有了统一的入口，规范可以把「执行栈上没有上下文时按排队顺序跑」写成同一句话，跨实例、跨浏览器、跨运行时都是一条队列。它没有改动清空规则，只是把入口摊平了。

## 把顺序摆出来跑一遍

规则读下来还是有点悬，索性在 Node v22.22.2 上把四种回调混在一起跑一次。

```js
'use strict';

// A：顶层脚本混排
console.log('sync start');
setTimeout(() => console.log('A setTimeout'), 0);
setImmediate(() => console.log('A setImmediate'));
process.nextTick(() => console.log('A nextTick 1'));
Promise.resolve().then(() => console.log('A promise 1'));
queueMicrotask(() => console.log('A queueMicrotask 1'));
process.nextTick(() => console.log('A nextTick 2'));
console.log('sync end');

// B：定时器回调内部再混排
setTimeout(() => {
  console.log('B timer start');
  process.nextTick(() => console.log('B nextTick'));
  Promise.resolve().then(() => console.log('B promise'));
  queueMicrotask(() => console.log('B queueMicrotask'));
  console.log('B timer end');
}, 0);

// C：两条队列互相再入队
Promise.resolve().then(() => {
  console.log('C promise outer');
  process.nextTick(() => console.log('C nextTick from promise'));
});
process.nextTick(() => {
  console.log('C nextTick outer');
  Promise.resolve().then(() => console.log('C promise from nextTick'));
});

// D：递归微任务会不会挡住定时器
let n = 0;
function recurse() {
  if (n++ < 3) {
    queueMicrotask(recurse);
    console.log('D recurse ' + n);
  }
}
queueMicrotask(recurse);
setTimeout(() => console.log('D setTimeout (after recursion)'), 0);
```

打印出来是这样：

```
sync start
sync end
A nextTick 1
A nextTick 2
C nextTick outer
A promise 1
A queueMicrotask 1
C promise outer
D recurse 1
C promise from nextTick
D recurse 2
D recurse 3
C nextTick from promise
A setImmediate
A setTimeout
B timer start
B timer end
B nextTick
B promise
B queueMicrotask
D setTimeout (after recursion)
```

先看最上面两行。`sync start` 和 `sync end` 是同步的，中间排进去的几条回调一个都没插进来，因为栈还没空。接着 `A nextTick 1`、`A nextTick 2`、`C nextTick outer` 连着出来，两条 nextTick 加 C 组那条，整批先走完，然后才轮到 `A promise 1`、`A queueMicrotask 1`、`C promise outer`。这就是里层那个 while 先取空、再 `runMicrotasks()` 的样子。

再看 C 组互相再入队的两条。`C promise from nextTick` 是在 nextTick 回调里排的 Promise，它落在 `D recurse 1` 之后，说明新排的微任务只加在队尾，不插队；`C nextTick from promise` 反过来，是在 Promise 回调里排的 nextTick，它落在 `D recurse 3` 之后、`A setImmediate` 之前，说明 do/while 又转了一轮把新排的 nextTick 补掉，但始终没让事件循环进入下一圈。这行夹在中间，光看规范不容易想到，得跑一遍才看得见。

B 组是另一件事。定时器回调里 `B timer start`、`B timer end` 两行同步打完，紧接着才是 `B nextTick`、`B promise`、`B queueMicrotask`。也就是说清空不只发生在顶层脚本结束那一次，每个回调返回、栈一空，就再来一次。前面说「位置是栈空的那一刻」，这一组把它落到了具体的一次回调上。

D 组的递归微任务 `D recurse 1`、`2`、`3` 跟 C 组的微任务交叉着出来，全部排在 `A setImmediate`、`A setTimeout` 前面，印证了检查点那个 while 会一直排到队列空。顶层 `setImmediate` 和 `setTimeout` 谁在前并没准，我这次跑是 `setImmediate` 在前，换一版脚本再跑就成了 `setTimeout` 在前，跟官方文档说的不保证对得上，别把某一次的输出当规律。

## 一直排到空的代价

顺序对上了，可还有个不太舒服的地方：这条队列没有「这一轮最多清几个」的上限。

检查点的 while 条件是队列非空，微任务里再排微任务就继续取，于是这一轮可以无限长。Node 那条 nextTick 队列也一样，递归 nextTick 能把事件循环钉死在进入 poll 之前，I/O 回调永远等不到；浏览器里递归微任务会把渲染和用户输入一起挡在后面，页面卡住却不报任何错。这不是实现偷懒，是「Promise 链必须在同一个任务里跑完」这条要求的另一面：IndexedDB 那个事务在派发结束就失效，靠的正是回调赶在同一圈里执行；要是允许中途让位给渲染，封装就又散了。设计上选的是把清空点钉在执行栈刚空的那一瞬，好处是时序可预期、回调一定连着跑完，坏处是这一圈能占多久完全交给写代码的人自己控制。官方文档给出的建议也就落在具体用法上：想排微任务用 `queueMicrotask()`，别拿递归的 `process.nextTick()` 去表达「尽快」。

这两条队列的分工我以前一直混着记，现在倒觉得分得挺清楚：浏览器用一条微任务队列把「紧接当前脚本」的事收在同一个任务里；Node 在这条之外又加了一条更早、更贴着 JS 边界的 nextTick 队列，用来放必须在事件循环继续前处理掉的东西，代价是它比谁都容易把循环堵住。

回头看 `processTicksAndRejections()` 的循环条件，末尾还挂着 `hasRejectionToWarn() && processPromiseRejections()`，未处理的 Promise rejection 也是在这一轮里一起报掉的。为什么把 rejection 的警告塞进同一个 do/while，我没往下查证，先记着。
